# 제조 AI Agent 실습 전체 제작과 배포 설계

작성 기준: 2026년 11월 21일 KST · v0.1 · 상태: 설계 완료, 새 실습 앱과 모델 응답팩은 제작 전

**공통 웹앱 하나에 시나리오 팩을 넣고, 수강생은 브라우저에서 회사 자료 등록부터 보고서 저장까지 진행한다.** GitHub는 코드와 교재의 배포처다. 수업 기본 모드는 사전에 확보한 실제 모델 응답을 사용하고, 문서 추출·DB 조회·규칙 판정·질문·보고서는 수강생 입력으로 실행한다. 새 모델 추론은 같은 화면에 연결하는 선택 기능이다.

이 설계는 [기존 강의 구성안](MANUFACTURING_AGENT_HANDS_ON_PLAN.ko.md)을 준비된 영상에 맞춰 구체화한다. 실제 자산은 [영상 자료팩](../scenarios/index.json)과 [미리보기](../index.html)에 있다. 여기서 설명하는 앱, 실행 명령, API, 스키마, 수업용 모델 응답은 제작할 대상이며 현재 동작한다고 주장하는 항목이 아니다.

## 1. 먼저 확정할 구성

| 구분 | 기본 결정 | 이유 |
|---|---|---|
| 수업 진입 | 링크 하나 → 예제 선택 → 실행 | GitHub 계정, 코드 수정, 개인 GPU/API 키 없이 시작 |
| 앱 | 한국어 화면 하나, 데이터가 다른 실습팩 | 같은 흐름을 조립·계측·재검수에 반복 적용 |
| 모델 체험 | 실제 저장 응답을 기본 제공, 새 추론은 선택 | 수업 시간과 서버 상태에 영향을 덜 받음 |
| 실제 동작 | 문서 추출, DB, 규칙, 질문, 저장, 보고서 | 준비된 보고서 PDF를 단순히 보여 주는 수준을 넘음 |
| 문서 범위 | 우리가 제공하는 텍스트 PDF·정형 표 | 입력이 같으면 구조화 결과가 같도록 설계 |
| 배포 | 공개 코드 저장소 + 웹앱 + 버전 고정 ZIP | 소스 확인, 바로 체험, 인터넷 장애 대응을 각각 해결 |
| 영상 | 원본 보존 + 브라우저용 파생본 + 분석 프레임 | 재생 호환성과 증거 추적을 함께 확보 |
| 실습 3종 | 전자 조립 / 계측 판독 / 기계 조립과 재검수 | 현재 확보한 자료로 시작 가능 |
| 확장 | 동일 제품 다지점 측정, 키팅·포장 | 해당 장면을 연결한 신규 촬영이 선행되어야 함 |

수업의 성공은 전 항목이 녹색으로 바뀌는 것이 아니다. 참가자가 **무엇을 관찰했고, 무엇은 확인하지 못했으며, 왜 질문했고, 최종 기록에 어떻게 남겼는지** 설명하고 산출물을 저장하는 것이다.

## 2. 현재 있는 것과 만들어야 하는 것

| 항목 | 현재 상태 | 필요한 다음 작업 |
|---|---|---|
| 원본 미디어 | 영상 7개·사진 2개, 약257.3 MB 확보 | 수업 장면 전체 검수, 재생용 파생본 제작 |
| 전달 ZIP | 원본·프레임·출처 포함 약269.7 MB | 실행 앱과 실제 응답을 포함한 새 배포본 제작 |
| 전자 조립 | 정상 주석 121초, 오류·수정 주석 227초, 원본8단계, 부품9종 대응표 | 교육용 문서, 관찰 기준, 앱 연결 |
| 기계 조립·정비 | 184.5초 / 136.7초, 부품·상태 PDF7쪽, 행동 주석 | 교육용 작업군/기준, 브라우저 재생본 |
| 계측 | 장비 사진2개와 영상3개, 일부 시각별 원본 라벨 | 장비별 판독 검수, 라벨과 미디어 시각 정렬 |
| 자료 HTML | 원본 탐색·미리보기 카탈로그 | 상태·질문·판정·보고서가 있는 실습 앱 |
| 실제 모델 응답 | 이 새 자료팩에 맞춘 응답팩은 없음 | 문서/입력 확정 후 실제 요청과 응답 수집 |
| 도면 다지점 측정 | 같은 제품·도면·접촉 장면이 연결된 자료 없음 | 간단한 제품 하나를 직접 촬영 |
| 키팅·포장 | 완결된 공개 가능 사례 없음 | 주문표·부품·누락·라벨을 연결해 촬영 |

자료팩의 표본 프레임 검수와 원본 오류 주석은 새로운 하네스의 성능 검증을 대신하지 않는다. 현재 GPU 중단 지시는 유지한다. 이 설계 작업은 모델 서버 재가동이나 외부 게시를 실행하지 않는다.

## 3. 시스템을 여섯 부분으로 나눈다

| 부분 | 입력 | 실제 처리 | 출력 | 생성형 모델 |
|---|---|---|---|---|
| 회사 정보 구축 | SOP PDF, 부품표, 검사기준, 장비표 | 추출, 정규화, 참조·단위 검사 | 회사 정보, SQLite, 작업별 설명 | 기본 없음 |
| 작업 설정 | 회사·제품·공정·문서 버전 | ID 기반 조회, 순서/규칙 선택 | 이번 작업의 기준 묶음 | 없음 |
| 관찰 | 현재/이전 영상 프레임, 작업 정보 | 저장 응답 조회 또는 모델 호출 | 작업·부품·관계·수치 후보 | VLM/OCR |
| 검증과 상태 | 관찰 후보, 증거, 적용 조건 | 대상·시점·단위 검사, 상태 전이 | 확인/불일치/보류, 다음 행동 | 기본 없음 |
| 상호작용 | 보류 이유, 질문, 답변/새 증거 | 한국어 안내, 연결 검증, 재판정 | 대화와 조치 기록 | ASR 선택 |
| 출력 | 구조화된 실행 기록 | 누락 검사, 템플릿 렌더링 | 검수조서·보고서·증거 ZIP | 없음 |

강의에서는 이 기능들을 ‘관찰 담당·계측 담당·검증 담당·질문 담당·기록 담당’으로 설명한다. 이들이 모두 별도 LLM 프로세스일 필요는 없다. **오케스트레이터는 정해진 상태와 규칙으로 도구를 호출하는 제어기**다. 관찰과 재확인에 같은 Qwen 서버를 사용할 수 있고, 조회·계산·문서 생성은 일반 코드가 수행한다.

## 4. GitHub와 실행 환경의 역할

| 위치 | 넣을 것 | 넣지 않을 것 |
|---|---|---|
| 공개 GitHub 저장소 | 코드, 스키마, 소형 교육 문서, 활동지, 설치·제작 방법 | HTech 자료, 계정정보, 연구 실행 디렉터리 전체, 모델 가중치 |
| GitHub Pages | 시작 화면, 기본 실습 앱, 작은 기본 시나리오팩 | Python/vLLM 서버 프로세스 |
| GitHub Releases | 버전별 전체 영상팩, 응답팩, 오프라인 실행팩, 체크섬 | 변경될 때마다 덮어쓰는 무버전 원본 |
| 강의용 웹 서버 | Pages와 동일한 앱, 로컬 미디어, 선택 추론 게이트웨이 | 학생별 연구 서버 설치 |
| 강사 모델 서버 | 고정 VLM/OCR, 요청 큐, 원시 응답 보존 | 브라우저에 노출되는 비밀키 |
| 수강생 브라우저 | 문서 처리, 실습 상태, 개인 DB, 보고서 다운로드 | 기본 모드에서 외부 전송되는 개인 문서/음성 |

추천 공개 저장소명은 `manufacturing-agent-workshop`이다. 실제 소유 계정과 URL은 게시할 때 정한다. 기존 제조 연구 저장소를 그대로 공개하지 않고, 허용한 코드와 자산만 새 배포 폴더로 복사한다.

GitHub Pages는 정적 앱 배포에 사용한다. 공식 한도는 게시 사이트1GB, 월 대역폭100GB의 soft limit이다. 따라서 대용량 원본은 Releases의 다운로드 파일로 분리하고, 웹 체험에는 작게 준비한 재생본을 쓴다. Releases는 파일당2GiB 미만이다. Releases를 영상 스트리밍 CDN처럼 가정하지 않고 원본팩 다운로드처로 쓴다. [Pages 공식 한도](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [Releases 공식 문서](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

## 5. 구현 기술과 설치 부담

**브라우저에서 기본 실습을 끝낼 수 있는 구성을 우선한다.** 실제 추론을 쓰는 수업은 같은 앱을 강의 서버에서 제공하고 `/api`를 연결한다.

| 기능 | 제안 구현 | 범위와 주의점 |
|---|---|---|
| 화면 | TypeScript + React + Vite | 빌드 결과는 HTML/CSS/JS, 새 라이브러리 버전은 제작 시 고정 |
| 공통 제어기 | 별도 TypeScript 패키지 | 브라우저와 Node 검수에서 동일 코드 실행 |
| PDF 보기·텍스트 추출 | PDF.js, 문서 템플릿별 필드 매핑 | 텍스트 PDF 대상, 임의 도면 의미 이해 기능 아님 |
| CSV·표 | 명시적 헤더/인코딩의 CSV 파서 | 수업 기본은 CSV, XLSX는 후속 어댑터 |
| DB | sql.js의 SQLite | 메모리 DB를 IndexedDB에 저장하고 파일로 내보냄 |
| 영속 기록 | IndexedDB 이벤트 원장과 스냅샷 | 새로고침 후 복구, ZIP/JSON 수동 백업 제공 |
| 스키마 | JSON Schema + 공통 검증기 | Python 게이트웨이에도 같은 계약 적용 |
| 숫자 | 10진수 라이브러리 또는 정수 스케일 | JS 부동소수점 오차로 경계값 판정이 바뀌지 않게 함 |
| QR | 브라우저 WASM 디코더 후보 | 실제 준비 프레임에서 인식 확인 후 활성화 |
| 영상 | HTML video + 사전 추출 프레임 | 실제 분석 입력과 UI 재생용 영상을 구분 |
| 보고서 | 같은 기록을 쓰는 HTML 템플릿 | 브라우저 인쇄/PDF 저장, JSON/CSV/증거 ZIP |
| 새 추론 연결 | FastAPI 게이트웨이 + 기존 어댑터 | 디코딩/모델 호출/영수증 담당, 규칙 엔진을 중복 구현하지 않음 |
| 자동 PDF 다운로드 | 강사 서버의 선택 렌더러 | 브라우저 기본은 인쇄 대화상자를 거쳐 PDF 저장 |

PDF.js는 페이지 텍스트를 추출할 수 있고, sql.js는 브라우저에서 SQLite를 사용할 수 있다. 이것만으로 문서 의미 해석이나 자동 영구 저장이 완성되는 것은 아니므로 매핑·검증·저장 계층을 직접 구현한다. [PDF.js API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html), [sql.js 공식 문서](https://sql.js.org/documentation/).

이 선택은 이전 계획의 Python 중심 문서 처리를 **설치 없는 수강생 경로로 구체화한 것**이다. 기존 Python 연구 제어기를 통째로 브라우저에 옮겼다고 취급하지 않는다. 검증 가능한 작은 교육용 제어기를 만들고, 기존 계약·회귀 사례를 명시적으로 이식한다. Python 문서 처리나 노트북은 강사용 제작 도구·심화 자료로 남긴다.

## 6. 공개 저장소와 시나리오 팩 구조

아래는 만들 디렉터리 구조다.

```text
manufacturing-agent-workshop/
  README.ko.md
  START_HERE.ko.md
  LICENSE                         # 자체 코드의 라이선스
  DATA_LICENSES.md                 # 미디어별 조건, 코드와 별도
  CITATIONS.md
  apps/web/                       # 학생 화면, 강사 화면
  packages/core/                   # 문서 컴파일, 규칙, 상태, 질문, 보고서
  packages/contracts/              # JSON Schema, 버전·유효성 검사
  packages/adapters/               # recorded / fixture / live 공통 인터페이스
  services/inference-gateway/      # 선택 기능, 모델 호출과 원시 응답
  scenarios/
    electronics/
    instruments/
    mechanical/
  recordings/                     # 공개 가능한 실제 응답 색인·소형 응답
  fixtures/                       # 명시적으로 작성한 교육 이벤트
  templates/                      # 검사표·보고서·질문
  media/manifest.json              # 큰 영상은 릴리스로 분리
  instructor/                     # 예상 흐름·수업 운영·오류 해설
  exercises/                      # 학생 활동지
  tests/                          # 단위, 통합, 브라우저 E2E
  tools/                          # 패키징, 출처 검사, 응답 검수
  .github/workflows/               # 검증·정적 빌드·공개 배포
```

각 시나리오 팩은 다음을 포함한다.

```text
scenario.yaml                     # 이름, 버전, 목표, 자료 묶음
documents/                        # 교육용 SOP.pdf, BOM.csv, rules.csv
references/                       # 원본 그림·부품 사진, 출처
mapping/document-fields.json      # PDF·표 필드의 추출 규약
media-manifest.json               # 원본/재생본/프레임의 대응
workflow.json                     # 작업군, 선후관계, 재검사 조건
questions.ko.json                  # 질문 템플릿, 허용 답변
audio/                            # 한국어 안내 파일과 자막
recording-index.json              # 해당 입력에 대응하는 실제 응답 ID
exercise.json                     # 바꿀 입력, 학습 목표
```

원본 주석·정답·강사 해설은 모델용 입력 팩과 분리한다. 공개 저장소의 해설을 학생이 볼 수 있는 것은 허용하되, **평가 라벨이 모델 요청과 기본 실행 앱의 관찰 입력으로 들어가지 않도록** 빌드와 요청 검사를 둔다. 교육용 체크포인트 재생과 독립 성능 평가는 별개다.

## 7. 회사 자료를 어떤 파일로 만들 것인가

첫 예시는 가상의 교육 회사와 제품을 사용한다. 원본 자료에 없는 회사명·작업지시·검사 규정은 모두 교육용으로 표시한다.

| 파일 | 포함 필드 | 추출 후 역할 |
|---|---|---|
| `company.pdf` | 교육 회사 ID, 사업장, 문서 버전 | 자료 묶음의 소속 |
| `SOP.pdf` | 공정 ID, 작업군, 절차, 대상, 완료 조건 | 순서와 현재 작업의 요구사항 |
| `parts.csv` | 부품 ID, 이름/별칭, 필요 수량 또는 미확정 | 부품 조회와 구성 확인 |
| `criteria.csv` | 기준 ID, 적용 단계, 대상, 조건, 허용 증거 | 판정 규칙 |
| `instruments.csv` | 장비 ID, 단위, 눈금/표시 형식, 해석 규칙 | 계측 판독과 검증 |
| `work_order.pdf` | 작업지시 ID, 제품/교육 사례 ID, 사용할 문서 버전 | 이번 실행의 선택 |
| `reference.pdf/svg` | 원본 부품 형상 또는 교육용 도면 | 비교·위치 표시 |
| `report_template` | 검수조서·보고서의 출력 필드 | 동일 기록의 두 문서 표현 |

**자료 제작 순서:** 영상 전체 검수 → 원본 절차·확인 가능한 대상 정리 → 교육용 규정 확정 → PDF/CSV 작성 → 실제 추출 검증. 영상을 보고 모든 항목이 합격하도록 규정을 사후 조정하지 않는다. 개발에 사용한 영상은 교육용 사례로 표시하며 일반 성능의 독립 시험으로 부르지 않는다.

`정보 구축` 버튼은 다음을 실제 수행한다.

1. PDF에서 문자와 위치, CSV에서 행을 읽는다.
2. 템플릿 버전과 필수 열을 검사한다.
3. 필드를 제품·작업·기준·장비 ID로 정규화한다.
4. 단위, 중복 ID, 존재하지 않는 부품 참조, 순서 순환을 검사한다.
5. 화면에 추출값과 원문 페이지/행을 나란히 보여 준다.
6. 오류가 없으면 버전이 고정된 회사 정보와 SQLite를 만든다.
7. 그 정보에서 작업별 Markdown 설명을 생성한다.

읽지 못한 필드는 빈 값을 알리고 해결을 요구한다. 미리 만든 정답 JSON을 읽어 놓고 PDF를 분석했다고 표시하지 않는다. 지원하지 않는 스캔 PDF는 명확히 구분하고, 준비된 예제 선택으로 수업을 계속할 수 있게 한다.

정규화된 회사 정보가 기준이고 SQLite와 Markdown은 그 파생물이다. Markdown만 수정해 DB와 내용이 달라지는 구조는 피한다. 편집은 원본/편집 폼에서 새 버전을 만든 뒤 재컴파일한다. 진행 중인 세션은 시작 때 선택한 기준 버전을 유지한다.

NVIDIA Auto Ontology는 기본 실행의 의존성으로 두지 않는다. 제품–공정–작업–기준–증거 관계를 명시적으로 만든 뒤, 추후 그 DB를 연결하는 별도 심화 과제로 둔다. 임의 문서에서 회사 지식을 완성하는 기능까지 이번 수업의 성공 조건에 포함하지 않는다.

## 8. 수강생이 밟는 전체 단계

| 단계 | 화면의 버튼/행동 | 실제 시스템 작업 | 학생이 확인할 결과 |
|---|---|---|---|
| 0 | `실습 시작` | 브라우저·자료팩·저장 공간 확인 | 사용 가능/누락 항목 |
| 1 | `예제 회사 자료 가져오기` | 파일 선택 또는 준비된 자료 로드 | PDF·표·참조 이미지 |
| 2 | `정보 구축` | 추출·정규화·검증·DB 구성 | 작업 목록·기준표·원문 연결 |
| 3 | `회사 / 제품 / 공정 선택` | 정확한 ID와 문서 버전 조회 | 순서·부품·규약·검사 항목 |
| 4 | `작업 시작` | 세션·개체·시도 생성 | 현재 적용 기준과 시작 기록 |
| 5 | `영상 재생 / 다음 관찰` | 시각에 맞는 입력 생성과 관찰 | 현재 작업 후보·증거·불확실성 |
| 6 | 자동 `확인 필요` | 규칙에 맞는 질문 생성 | 한국어 음성/자막, 질문 이유 |
| 7 | `답변 / 추가 증거 선택` | 질문·대상·시도 연결 검사 | 확인된 내용과 남은 보류 |
| 8 | `다음 작업 진행` 또는 자동 갱신 | 작업 활동과 완료 상태를 따로 갱신 | 이전 미해결 항목을 보존한 진행 |
| 9 | `최종 검토` | 필수 항목·미측정·미처리 요청 검사 | 완료/불일치/보류의 근거 |
| 10 | `검수조서 / 보고서 생성` | 현재 기록으로 두 문서 렌더링 | 사진·값·답변이 연결된 문서 |
| 11 | `결과 저장 / 새 조건으로 비교` | ZIP 다운로드 또는 새 세션 분기 | 이전 결과를 보존한 비교 |

모델이 읽은 정보는 `내부 처리 보기`에서 펼쳐 볼 수 있게 한다. 여기에 현재 작업·관련 기준·참조 이미지·실제 전달 프레임·이전 증거·원시 응답을 표시한다. 기본 화면에서는 파일 해시나 긴 JSON을 숨긴다.

## 9. 화면을 어떻게 구성할 것인가

슬라이드 여러 장을 누르는 형태보다 **노트북처럼 왼쪽에 진행 단계가 있는 하나의 작업 화면**을 권장한다.

| 영역 | 구성 |
|---|---|
| 상단 | 실습 이름, 모드, 저장 상태, 현재 세션 |
| 왼쪽 단계 목록 | 자료 → 정보 구축 → 작업 설정 → 실행 → 검토 → 보고서 |
| 실행 화면 왼쪽 | 영상/원본 이미지, 현재 시각, 재생·일시정지·관찰 이동 |
| 실행 화면 가운데 | 작업군 순서, 예상 작업과 관찰 작업, 적용 조건 |
| 실행 화면 오른쪽 | 관찰 요약, 확인 질문, 답변/증거 제출 |
| 하단 기록 | 중요 장면, 수치, 질문, 조치의 시간순 카드 |
| 펼쳐보기 | DB 조회, 모델 입력/응답, 규칙 판정 근거, 출처 |

1280px 노트북에서는 영상과 체크리스트의 두 열을 우선하고 질문은 고정 카드로 둔다. 작은 화면은 순서대로 쌓는다. 색만으로 상태를 구분하지 않고 `충족 / 불일치 / 확인 필요 / 아직 검사할 때가 아님`을 함께 쓴다.

시간 제어에는 `교육용 빠른 진행`과 `원래 영상 속도`를 둔다. 표시된 짧은 처리 애니메이션을 실제 모델 지연시간으로 소개하지 않는다. 현재 시각보다 뒤의 모델 응답이나 최종 사진을 앞 단계 판단에 제공하지 않는다.

영상 뒤로 이동은 `복습 보기`이며 확정 기록을 자동으로 취소하지 않는다. 다른 답변/다른 조건을 시험하려면 `이 시점에서 새 실행 만들기`로 분기한다. 보고서 생성 버튼을 눌렀다고 남은 항목을 자동 합격 처리하지 않는다.

## 10. 세 가지 실행 모드와 결과 출처

| 모드 | 모델 역할 | 항상 실제 실행할 것 | UI와 보고서의 표시 |
|---|---|---|---|
| 실제 응답 재현 | 사전 실행한 원시 응답 사용 | 문서·조회·규칙·질문·보고서 | `저장된 모델 응답`, 모델/생성일 |
| 새 모델 실행 | 같은 요청을 서버로 전송 | 위 처리 + 새 추론/오류 저장 | `새 모델 실행`, 대기/실행시간 |
| 제어 실습 | 명시적으로 작성한 사건/값 사용 | 제어기와 기록/보고서 | `교육용 입력` 또는 `작업자 입력` |

이 세 모드는 같은 응답 스키마를 사용하지만 `origin`을 지우지 않는다. 한 실행 안에서 혼합된다면 이벤트와 보고서에 각각의 출처를 남긴다. 사용자가 `계속 진행`을 눌러 대체 모드를 택할 수는 있지만, 서버 장애 때 조용히 교육용 성공 응답으로 교체하지 않는다.

**화면은 실제 제품처럼 만들고 모델 결과의 출처는 짧고 명확하게 표시한다.** 학생이 직접 답하고 기준을 바꾸므로 재현 모드도 상호작용이 있다. 질문 템플릿과 보고서 템플릿은 정상적인 코드 기반 출력이며 LLM이 방금 작성한 내용이라고 표시할 필요가 없다.

## 11. 실제 모델 응답팩을 만드는 방법

### 모델 역할

| 역할 | 준비 방향 | 아직 검증해야 하는 것 |
|---|---|---|
| 작업·관계 관찰 | 기존 프로젝트의 Qwen FP8 계열 어댑터 참고 | 새 교육 문서/프레임/한국어 계약의 실제 전달 |
| 디지털 표시 판독 | 확보된 GLM-OCR를 주 후보, PP-OCRv6 medium CPU를 대안 후보로 점검 | 새 사진의 소수점·단위·ROI 판독 |
| 아날로그 계기 | 장비 해석 규칙 + VLM 후보 또는 수동 확인 | 눈금 정렬/해상도/측정물·장비 연결 |
| 보고서·질문 | 한국어 템플릿 | 기록과 값·출처 일치 |

내부 보존 기준은 [Qwen FP8 선택 기록](PROJECT_NOTES.ko.md)이며 그 파일의 로컬 checkpoint 식별자는 `Qwen/Qwen3.8-27B-FP8`다. 이는 현재 온라인 서버의 존재나 새 영상 성능을 뜻하지 않는다. OCR 후보의 실제 저장소·revision은 [고정 다운로드 설정](PROJECT_NOTES.ko.md)을 따른다. 후보 세 개를 전부 상시 띄울 필요는 없다. 교재용 샘플에서 실행 가능성과 결과를 확인한 뒤 사용할 하나를 고정한다.

짧은 관찰용 기존384토큰 설정을 모든 상세 검사에도 강제하지 않는다. 관찰과 상세 확인의 출력 스키마·예산을 별도로 확인하고 실제 요청 크기, 종료 사유, 잘림을 기록한다. 새 교육 경로의 성능이나 정확도를 기존 HTech 결과에서 가져오지 않는다.

### 응답 수집 절차

1. 문서·규칙·미디어·프롬프트·스키마를 버전 고정한다.
2. 전체 영상의 수업용 관찰 시각과 질문 후보를 정한다. 원본 오류 주석을 사용해 선정했으면 개발용 선정이라고 기록한다.
3. 현재 프레임, 필요한 이전 프레임, 참조 그림, 작업 정보가 포함된 **실제 직렬화 요청**을 먼저 검수한다.
4. 실제 모델을 실행해 원시 응답·실패·종료 사유·토큰·시간을 보존한다.
5. 파싱과 증거 검증 결과를 원시 응답과 별도로 저장한다.
6. 바뀌지 않은 모델 요청을 재생할 수 있도록 색인을 만든다.
7. 고정 분기의 질문·답변이 이후 입력을 바꾸면 해당 분기도 별도 기록한다.
8. 누락 응답, 잘못된 인식, 보류를 포함해 수업 흐름을 리허설한다.

응답팩 항목은 `request.json`, `response.raw.json`, `parsed.json`, `validation.json`, `timing.json`, `media-index.json`을 연결한다. 모델명/revision, 추론 설정, 입력 이미지와 문서 해시, 전처리 버전, 실제 프레임 시각과 역할을 보존한다. 공개본에서 서버의 사적인 경로를 제외할 때는 참조 치환표와 동일 콘텐츠 해시를 남기며 모델이 받은 의미 내용은 바꾸지 않는다.

### 학생이 입력을 바꿨을 때

| 변경 | 처리 |
|---|---|
| 순수 표시 설정, 보고서 제목 | 기존 관찰 유지, 문서만 다시 렌더링 |
| 모델에 주지 않았던 숫자 허용 범위 | 같은 원시 판독 유지, 새 기준 버전으로 규칙 재평가 |
| 영상·ROI·모델·프롬프트 변경 | 일치하는 실제 응답이 없으면 새 추론 또는 명시적 제어 실습 |
| 모델 입력에 포함한 SOP/기준 변경 | 기존 모델 응답 재사용 불가 |
| 작업자 답변으로 후속 상태 변경 | 후속 실제 요청이 같을 때만 재현; 다르면 분기 응답/새 추론 필요 |
| 과거 영상만 다시 보기 | 새로운 관찰 결과를 만들지 않는 복습 |

캐시 키에는 모델 설정과 프롬프트뿐 아니라 **해당 요청에 실제 포함된 문서·상태·현재/과거 프레임·참조 이미지·전처리**를 포함한다. ‘영상 파일이 같음’만으로 동일 요청으로 처리하지 않는다. 첫 수업은 분기를 작게 제한하고, 자유 변경은 제어 실습 또는 새 추론 탭으로 둔다.

학생마다 다른 세션 ID·화면 이벤트 ID·벽시계 시각은 모델 의미 입력과 분리한다. 요청 작성 단계부터 안정적인 시나리오 대상/증거 ID를 사용하고, UI 실행 ID와의 대응표를 원장에 저장한다. 원시 모델 응답은 고치지 않고 실행에 적용할 때만 그 대응표를 이용한다. 실제 모델 입력에 들어간 대상 식별자나 답변을 나중에 해시에서 임의로 제외하지 않는다. 이러한 분리가 없는 예전 응답은 ‘비슷한 입력’이라는 이유로 재사용하지 않는다.

## 12. 시나리오 A 전자 조립

개발 첫 사례는 원본 절차와 오류 주석이 비교적 분명한 전자 조립으로 한다.

| 항목 | 구성 |
|---|---|
| 자료 | EgoOops `S1790005` 약121초, `S1790010` 약227초 |
| 교육 작업군 | 회로 연결 → 프로펠러 장착 → 배터리 삽입 → 스위치/작동 확인 |
| 원본 조건 | S1/모터 연결, S2/L1 병렬 연결, 배터리2개, S1/S2 조작 순서 |
| 문서 | 전자 조립 SOP, 부품표, 연결 관계표, 시각적 검사표, 작업지시 |
| 핵심 상호작용 | S1/S2 식별, 가려진 연결부/배터리 방향 질문, 수정 후 재검토 |
| 출력 | 조립 검수조서, 정상·오류 두 실행 비교, 질문/수정 기록 |

정상 주석 영상은 첫 완주용, 오류 주석 영상은 두 번째 비교용이다. 두 영상을 동일 제품의 전후 장면으로 잇지 않는다.

오류 영상의58.3–86.6초에는 병렬 대신 직렬 연결했다는 원본 주석이 있다. 이를 **강사 해설 기준**으로 사용하고 모델 입력에 정답을 넣지 않는다.192.2–198.7초의 배터리 방향 관련 주석과199.5–206.4초 수정 행동도 원래 시간·라벨을 보존한다. 프레임만으로 해당 오류가 충분히 보이는지는 전체 검수 후 별도로 판정한다.

부품표9종이 모두 몇 개씩 필요한지 자동으로 확정하지 않는다. 원본에서 명시된 배터리2개와 미확정 수량을 구분한다. microQR 대응표는 준비되어 있지만 영상 디코딩 성공은 확인 전이므로 기본 입력은 부품/작업 선택 버튼으로 제공한다.

질문 예: “현재 연결부에서 S2와 L1의 관계가 잘 보이지 않습니다. 연결부가 보이는 장면을 선택해 주세요.” 학생이 ‘확인했다’고 답하면 작업자 확인 기록을 만들고, 시각 증거 필수 조건은 사진이 없으면 보류를 유지한다.

## 13. 시나리오 B 계측 판독과 확인

### 현재 자료로 만드는 기본 실습

| 사례 | 입력 | 학습 목표 | 연결하지 않을 주장 |
|---|---|---|---|
| 디지털 캘리퍼스 | 표시26.30mm가 보이는 사진 | 원시 문자열·소수점·단위·범위 비교 | 교정된 실제 치수가 입증되었다는 주장 |
| 저속 버니어 | 약24.5초 영상 | 본척/보조척, 움직임, 관찰 시각 | 다른 사진의 제품과 동일 개체라는 주장 |
| 마이크로미터 | 본척/회전척 사진 | 눈금 계산과 확인 질문 | 사진에 보이지 않는 측정물의 특정 치수 |
| 빠른 계기 | 약5.3초 /7.7초 영상 | 판독 불가와 추가 확인 | 프레임마다 정확한 실측이 가능하다는 주장 |

서로 다른 사례마다 독립 `measurement_case_id`를 준다. 교육용 허용 범위는 가상 규정으로 표시한다. 예를 들어 디지털 사진의 교육용 범위를26.0–26.5mm에서26.0–26.2mm로 바꾸면 같은26.30이라는 판독 후보에 대해 규칙 결과가 달라진다. 이것은 규칙 실습이며 모델을 더 정확하게 만든 결과가 아니다.

학생은 장비 정보 로드 → 원본 확대 → 판독 → 값·단위 검증 → 확인 질문 → 기록 순서로 진행한다. 아날로그 눈금 해석은 OCR 문자 인식과 별도 문제로 설명한다. 원본 XLSX의 보간 라벨과 영상 시각을 맞추기 전에는 정답 시각을 추정해 점수를 내지 않는다.

### 수치 검증 원칙

- `raw_text`, 수치 후보, 단위 후보, 원본 ROI, 장비 ID를 함께 보존한다.
- 숫자 판독 모델에는 가능한 한 목표 허용 범위를 주지 않는다. 계기 눈금·단위 정보는 준다.
- 허용 범위에 맞추려고 소수점을 이동하지 않는다. `6188 → 61.88`은 계기 소수점 규칙과 이미지 근거가 있을 때만 별도의 해석 후보가 된다.
- 대상·장비·단위·현재 시도의 유효성이 확인된 뒤에 기준을 비교한다.
- 작업자가 수정한 값은 새 `worker_confirmed` 기록으로 만들고 OCR 원문은 남긴다.
- 단순 구간 비교와 계측의 교정·불확도 판정을 구분한다. 수업 기본은 교육용 구간 비교다.

### 도면에 위치별 기록하는 확장

사용자가 원한 완전한 흐름은 유지한다. 다만 이 기능의 실제 영상 검증에는 별도 촬영이 필요하다.

최소 촬영은 **제품 하나 + QR 하나 + 도면F01/F02/F03 + 디지털 캘리퍼스 하나**면 충분하다. 각 부위를 접촉하는 장면과 표시판이 연결되도록 촬영하고, F03→F01→F02 순서로 진행한다. 한 위치에는 흐릿한 장면과 선명한 재확인 장면을 준비한다. 세 종류의 장비를 같은 제품에 억지로 붙이는 것보다 위치 연결을 먼저 완성한다.

기본 연결은 학생의 부위 선택 또는 치구 마커와 접촉 확인으로 한다. 그 뒤에 VLM 부위 자동 제안을 비교한다. 단순히 QR이 보였다고 측정 접촉점까지 확정하지 않는다. 이 촬영 전의 도면 UI 실습은 `교육용 위치 선택`이라고 표시하고, 기존 독립 사진들을 동일 제품의 측정 증거로 사용하지 않는다.

## 14. 시나리오 C 기계 조립과 재검수

같은 UI에서 두 개의 **독립 작업 세션**을 제공한다.

| 세션 | 자료와 작업군 | 가르치는 점 |
|---|---|---|
| 차체 조립 | `01_assy_0_1`,184.5초. 차체→전방 브래킷→첫 축→풀리축→최종 외관 | 넓은 작업군 진행과 검사 조건의 구분 |
| 부품 교체 | `01_main_0_1`,136.7초. 축 분리→긴 부품 제거→짧은 부품 장착→재조립 | 변경 후 기존 증거 효력과 재검사 |

첫 영상의0–2.8초는 부품이 놓여 있는 시작 상태다. 준비 행위를 촬영한 영상이나 모든 도구의 준비 완료 증거라고 하지 않는다. 약63초 가림과181초 최종 외관은 수업 검수 후보로 사용한다. 손에 가렸다는 이유만으로 체결 누락으로 판정하지 않는다.

두 번째 작업의 목표는 긴 차체 부품을 **짧은 부품으로 교체**하는 것이다. 같은 긴 부품으로 원상 복구한다고 문서를 만들면 원본과 충돌한다. 분리/교체가 발생하면 영향을 받는 체결·형상 조건을 다시 열고, 새 시도에서 확보한 증거로 검토한다. 과거 사진은 이력에 남긴다.

문서는 원본 상태 PDF를 참조한 교육용 SOP, 부품 대응표, 교체 작업지시, 재검사 규칙표를 만든다. 나사/핀의 외관과 내부 체결 강도·토크는 별도 조건이다. 실제 토크 장면이 없으므로 토크 합격을 생성하지 않는다. 재삽입 행동을 곧바로 불량 정답으로 만들지 않는다.

출력은 조립 검수조서와 정비 기록이다. 둘을 비교 화면에서 볼 수 있지만 원본 간 동일 개체 여부를 입증한 연결은 만들지 않는다.

## 15. 확장팩 키팅과 포장

현재 세 팩의 공통 앱이 완성된 뒤 추가한다. 테이블 위에4–6종 부품, 주문 QR, 칸이 있는 트레이, 상자와 라벨을 준비하면 촬영이 비교적 단순하다.

필요한 장면은 주문 확인 → 구성품 배치 → 한 부품 누락/다른 규격 → 확인 질문 → 보충 → 포장 전 사진 → 라벨 확인이다. BOM과 라벨은 교육용으로 직접 만든다. 상자를 닫은 후 사진만으로 내부 수량을 확인했다고 처리하지 않는다.

이 팩은 수량·제품·로트 연결을 가르치는 장점이 있지만, 강의 전 촬영이 확보되지 않으면 필수 실습에서 제외한다. 다운로드하지 못한 웹 후보를 사용 가능한 영상으로 계획하지 않는다.

## 16. 핵심 데이터와 계약

| 계약 | 필수 내용 | 검증 |
|---|---|---|
| CompanyBundle | 회사/제품/버전, 문서, 작업, 부품, 기준, 장비 | 모든 참조 존재, 출처 페이지/행 연결 |
| Session | 세션, 시나리오 버전, 개체, 작업지시, 기준 버전, 모드 | 실행 중 기준이 몰래 바뀌지 않음 |
| Observation | 요청 ID, 관찰 시각, 현재/과거 프레임, 대상/행동 후보, 출처 | 미래 프레임 제외, 실제 응답 연결 |
| Measurement | 원문, 후보 값/단위, 장비, ROI, 위치, 검증 결과 | 판독과 범위 비교 분리 |
| Assessment | 기준, 대상/시도, 적용 상태, 관찰 상태, 판정, 증거 | 보류와 미도래를 불일치로 바꾸지 않음 |
| Question | 질문 ID, 작업/대상/시도, 이유, 필요한 답변/증거 | 다른 질문·제품의 답변 거부 |
| Evidence | 원본 해시, 시각/PTS, 역할, 파생 이력 | 참조 그림과 실행 장면 구분 |
| Report | 기록 버전, 최종 검토 범위, 항목별 상태, 증거·질문·한계 | DB/원장과 숫자·사진 일치 |

제안하는 교육용 기준의 예시는 다음과 같다. **실제 회사 기준이나 모델 예측이 아니다.**

```json
{
  "criterion_id": "ELEC-BATTERY-COUNT",
  "requirement_source": {
    "authority": "source_instruction",
    "source_ref": "electronics_instruction_6"
  },
  "target_type": "battery_holder",
  "due_phase": "battery_installation_review",
  "predicate": {"kind": "count_equals", "component": "battery", "value": 2},
  "evidence_policy": {
    "authority": "authored_training_policy",
    "version": "education-v1",
    "required_evidence": ["same_target", "visible_holder_slots"],
    "worker_statement_sufficient": false,
    "on_insufficient_evidence": "request_clear_view"
  }
}
```

실제 모델 관찰의 계약에는 `observed_task_id`, `target_candidates`, `visible_facts`, `uncertainties`, `evidence_refs`를 둔다. 모델이 `session_complete=true` 하나로 전체 작업을 종료할 권한은 주지 않는다. 출력 스키마에서 JSON이 맞는지와 사진으로 뒷받침되는지는 따로 검사한다.

DB는 최소 `documents`, `products`, `tasks`, `task_dependencies`, `criteria`, `instrument_profiles`, `sessions`, `events`, `evidence`, `measurements`, `questions`, `answers`, `assessments`, `reports`를 갖는다. 워크플로는 행 번호가 아니라 안정적인 ID로 참조한다. 조회에는 바인딩한 파라미터를 사용한다.

## 17. 제어기와 질문의 상태 전이

진행과 품질은 별도로 관리한다.

| 축 | 상태 예시 | 의미 |
|---|---|---|
| 작업 활동 | 예정 / 진행 관찰 / 다음 작업 관찰 / 종료 검토 | 지금 무엇을 하는가 |
| 적용 여부 | 해당 / 미도래 / 비해당 / 미확정 | 이 조건을 지금 이 대상에 검사해야 하는가 |
| 관찰 가능성 | 충분 / 일부 / 안 보임 | 장면으로 판단할 근거가 있는가 |
| 검사 결과 | 충족 / 불일치 / 보류 / 상충 | 근거와 교육 규정으로 어떤 결론을 냈는가 |
| 실행 처리 | 미실행 / 대기 / 실행 / 성공 / 오류 | 모델·도구가 정상적으로 결과를 냈는가 |

다음 작업이 보이면 활동 표시는 진행할 수 있다. 이전 조건의 보류는 미해결 목록에 남긴다. 검사 필수 조건을 충족하지 않은 상태에서 작업 완료를 자동 승인하지 않는다. 원본 순서를 알고 있다는 사실만으로 앞 단계를 수행했다고 채우지 않는다.

질문은 `생성 → 화면/음성 전달 → 답변 수신 → 대상 연결 검사 → 해결 또는 보류`를 거친다. 음성 파일 재생이 실패하면 음성 전달 완료를 기록하지 않는다. 화면 질문 확인은 별도 전달 채널이다. 질문마다 제품/대상/시도와 요구 증거가 붙는다.

학생은 텍스트, 수치+단위 폼, 준비된 후속 장면 선택으로 답할 수 있다. 녹음/ASR은 선택이다. 사전에 촬영된 후속 장면은 **사전 촬영 증거**로 표시하고 질문 때문에 새로 촬영된 것처럼 표현하지 않는다. ASR 결과를 사용할 때는 학생이 전사를 확인한 후 해당 질문에 제출한다.

후속 장면 선택은 세션의 관찰 시각을 그 장면까지 전진시키는 동작이다. 중간의 수업용 필수 사건은 순서대로 처리하고, 관찰하지 않은 구간은 별도로 표시한다. 이 구간을 실제 촬영 공백이나 수행 완료로 바꾸지 않는다. 질문은 새 증거를 받은 시각에 해결하며 과거 질문 발생 시각으로 소급하지 않는다. 아직 도달하지 않은 장면은 현재 모델 입력으로 제공하지 않는다.

한국어 질문 음성은 미리 준비한 파일과 자막을 우선한다. 시작 버튼에서 음성 재생을 활성화하고 볼륨/재생 테스트를 한다. 브라우저 TTS는 보조 경로다. 마이크는 안전한 컨텍스트와 사용자 권한이 필요하므로 HTTPS/localhost 환경을 확인하며, 권한이 없으면 텍스트로 계속한다. [브라우저 마이크 API](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia).

중복 클릭과 새로고침으로 질문·측정·보고서가 두 번 만들어지지 않게 `event_id`와 원장 revision을 사용한다. 재작업은 기존 결과를 지우는 대신 무효화 관계를 추가하고 영향을 받는 검사만 다시 연다. 브라우저 이벤트 원장에 먼저 확정 저장한 뒤 SQLite 화면용 상태를 투영하고, 중간 중단 시 원장에서 재구성한다.

## 18. 영상과 프레임의 배포

원본, 재생본, 모델 입력을 구분한다.

| 자료 | 사용 목적 | 보존할 연결 |
|---|---|---|
| 원본 영상 | 출처 확인, 재분석 | 원본 SHA256·길이·코덱·라이선스 |
| 재생본 | 브라우저에서 빠르게 보기 | 원본 ID, 변환 설정, 시간 대응, 파생 SHA256 |
| 분석 프레임 | 모델에 실제 전달 | 원본 시각/PTS, 크기, 크롭/회전/리사이즈 |
| 증거 프레임 | 판정·보고서에서 열기 | 실제 사용한 evidence ID, 같은 픽셀 해시 |
| 참조 이미지 | 부품/기준 형상 설명 | `reference` 역할, 원본 문서 페이지 |

IndustReal 두 원본은 MPEG-4 Part2라 브라우저용 H.264 파생본 제작이 필요하다. 원본은 유지하고 재생본을 별도로 저장한다. 시간축을 바꾸지 않는 변환을 우선하고, 프레임 누락·회전·길이를 검사한다. 계측 분석은 낮춘 재생 해상도만 사용하지 않고 원본 해상도의 ROI를 유지한다.

영상 전체를 huge base64 HTML에 넣는 형태는 기본 배포로 삼지 않는다. 약257MB 원본의 base64 표현만 해도 약343MB가 되어 시작과 갱신 부담이 커진다. 사용자 경험은 링크 하나로 유지하되 내부 파일을 나눈다. **단일 HTML은 최종 보고서**에 적용하고, 그 보고서에는 선택한 증거 사진과 구조화 결과만 임베드한다.

웹에는 작은 기본 재생본을 같은 출처로 제공한다. 원본 ZIP은 다운로드하거나 교실 로컬 서버에서 제공한다. 영상 탐색에는 HTTP Range 지원이 도움이 되므로 실제 배포 서버의 구간 요청·탐색을 확인한다. 외부 출처 영상의 캔버스 추출은 CORS 영향을 받으므로, 기본 보고서는 준비된 검증 프레임을 사용한다. [Range 요청 설명](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests).

보관 상태는 `원본 확보 / 미리보기만 있음 / 다운로드 실패 / 새 촬영 필요`로 구분한다. HTech와 파생 자료는 배포 허용 목록에 넣지 않는다. CC BY/CC BY-SA/CC0/Apache 등 개별 미디어 고지를 유지하고 자체 코드의 라이선스로 덮어쓰지 않는다.

## 19. 출력 문서와 제출물

검수조서와 보고서는 같은 실행 기록에서 생성한다. 보고서 문장에 자유로운 생성 모델을 필수로 두지 않는다.

| 출력 | 포함 내용 | 용도 |
|---|---|---|
| 검수조서 HTML/PDF | 작업지시, 대상, 기준 버전, 항목/기준/값/판정/증거, 미확인 항목 | 한 장 또는 소수 페이지로 검사 결과 확인 |
| 작업 보고서 HTML/PDF | 작업 개요, 시간순 진행, 주요 사진, 질문·답변·조치, 최종 상태 | 과정 설명과 전달 |
| 측정 기록 CSV | 원시값, 확인값, 단위, 장비, 사례/부위, 기준, 시각, 출처 | 후속 데이터 활용 |
| 도면 표시 SVG/PNG | 위치별 값·상태·증거 연결 | 동일 제품 확장팩 또는 명시적 수동 위치 실습 |
| 실행 기록 JSON | 기준/코드 버전, 사건, 시도, 실패, 보류, 응답 출처 | 재현·검수 |
| 증거 ZIP | 참조된 사진, 음성 답변 선택본, 기록, 출처 | 과제 제출 또는 팀 공유 |
| 단일 HTML 보고서 | 핵심 사진과 값이 내장된 최종 보고서 | 폴더 없이 결과 열람 |

검수조서의 행은 다음 형식을 기본으로 한다.

| 검사 항목 | 적용 기준 | 관찰/측정 | 결과 | 근거·확인 방식 |
|---|---|---|---|---|
| 배터리 수량 | 원본 지시:2개 | 실제 기록에서 표시 | 충족/보류 등 | 사진 또는 작업자 확인을 구분 |
| 연결 관계 | 교육 SOP의 지정 관계 | 실제 관찰 요약 | 불일치/보류 등 | 관련 프레임과 질문 |
| 미측정 항목 | 필요한 측정 규정 | 미측정 | 보류 | 값이 없는 이유 |

위 표는 출력 양식 예시이며 실제 모델 결과가 아니다. 문서에는 `교육용 검수조서`, 실행 모드, 문서/모델 버전, 아직 확인하지 못한 항목을 포함한다. 확인자가 입력하지 않은 서명·교정번호·승인은 만들지 않는다. 필수 항목이 보류여도 보고서를 저장할 수 있지만 상태는 ‘검토 필요’다.

## 20. 실제 모델 호출과 교실 운영

새 추론 경로의 게이트웨이는 아래 기능만 노출한다. 경로명은 구현 제안이다.

| API | 역할 |
|---|---|
| `GET /api/capabilities` | 사용 가능한 어댑터와 모델, 실행 가능 상태 |
| `POST /api/jobs` | 버전 고정 요청 제출, 중복 제출 키 검사 |
| `GET /api/jobs/{id}` | 대기/실행/성공/실패와 결과 ID |
| `GET /api/receipts/{id}` | 공개 가능한 원시 응답·전처리·시간 기록 |
| `POST /api/jobs/{id}/cancel` | 새 대기 취소 또는 현재 상태 확인 |

브라우저에서 vLLM 포트를 직접 호출하지 않는다. 강사 서버가 허용된 시나리오/요청 크기/미디어를 확인한 뒤 모델에 전달한다. 클래스용 임시 세션과 모델 자격증명을 분리한다. 학생의 입력은 기본 로컬에 남고, 새 추론으로 보낼 데이터 범위는 실행 화면에 표시한다.

실험 서버가 살아 있다는 것과 학생 요청이 진행 중이라는 것은 다르다. 화면에는 대기 수, 마지막 완료 요청, 실패, 실제 저장된 응답 수를 표시한다. 모델은 연결이 준비되면 재사용하며 학생의 다음 버튼마다 초기화하지 않는다. 사용 가능한 GPU와 서버 구성은 재개 시점의 계약으로 정하고, 이 문서에서 과거 GPU 배정을 실행하지 않는다.

시간 초과 후 무조건 다시 추론하지 않는다. `request_id`로 이미 완료됐는지 먼저 확인하고, 알 수 없으면 `결과 미확인`으로 남긴다. 자동 재시도는 횟수·조건을 제한하며 동일 실패를 무한 반복하지 않는다. 교실용 실시간 목표는 강사 지정 소수 요청으로 먼저 측정한 뒤 정한다.

부하를 추정할 때는 학생 수만 보지 않는다. 예를 들어30명×6회×요청당8초÷동시2개라면 처리 작업량만 약12분이다. 이는 계산 예시이며 현 모델 측정치가 아니다. 전체 영상을 모든 학생이 매번 새로 추론하는 경로를 수업 기본으로 두지 않는다. 저장 응답은 각 브라우저에서 사용하고 새 추론은 선택한 장면으로 제한한다.

## 21. 연결이 끊겨도 진행하는 방법

| 문제 | 제공할 경로 | 기록할 것 |
|---|---|---|
| 모델 서버 미응답 | 입력이 일치하는 실제 응답 재현 또는 명시적 제어 실습 선택 | 중단된 요청과 모드 전환 |
| 인터넷 불가 | 강사 노트북의 미리 준비한 로컬 웹 서버 | 같은 앱/자료 버전 |
| 외부 영상 서버 불가 | 교실 사전 다운로드본 또는 학생 파일 선택 | 미디어 해시 검사 |
| 마이크/음성 불가 | 텍스트 답변·자막 | 실제 전달 채널 |
| 브라우저 새로고침 | 저장한 원장 복구 | 마지막 확정 revision |
| 저장 공간 부족 | JSON/ZIP 내려받기, 큰 미디어 자동 캐시 중단 | 저장되지 않은 항목 |
| 입력 불일치 | 왜 응답을 재사용할 수 없는지 안내 | 변경 필드와 재현 가능 여부 |

전체 ZIP에는 앱 빌드, 자료, 응답, 한국어 폰트/음성, 라이선스를 포함한다. WASM·PDF worker·미디어가 있으므로 전체 실습의 기본 실행은 HTTP/HTTPS다. `file://index.html` 더블클릭만으로 모든 기능이 된다고 약속하지 않는다. 오프라인 강사 실행기는 사전 검증한 로컬 서버로 제공하고 학생은 주소에 접속한다. 학생별 독립 로컬 실행은 사후 심화 경로다.

교실 LAN의 단순 HTTP에서는 마이크가 제한될 수 있으므로 오프라인 기본을 텍스트로 하고, 음성 입력까지 필요하면 신뢰되는 HTTPS 환경을 사전에 준비한다. HTML 보고서 단독 열람과 전체 실습 앱 실행은 구분한다.

온라인 Pages와 교실 로컬 서버는 출처(origin)가 달라 브라우저 저장 상태가 자동으로 공유되지 않는다. 중간 전환은 `세션 내보내기` → 다른 주소에서 `세션 가져오기` → 스키마/앱/시나리오/미디어 해시 검사 → 마지막 확정 기록 복구로 진행한다. 각 실습 종료 때 작은 진행 백업을 내려받게 하며, 버전이 맞지 않으면 새 세션으로 분리하거나 명시적인 변환을 거친다.

| W06 | 영상·질문·보고서 화면 | W02,W04 | 한 사례 E2E | 작성 이벤트로도 흐름 완주, 출처 표시 |
| W07 | 실제 모델 요청 어댑터 | W03,W04 | 실제 전송용 요청 | 문서·이미지·과거 증거·한국어 계약 확인 |
| W08 | 실제 응답팩 확보·검수 | W07, 모델 실행 재개 조건 | 원시 요청/응답/오류·검수표 | 인식 실패를 지우지 않고 재현 가능 |
| W09 | 재현 연결·분기 처리 | W06,W08 | 기본 수업 모드 | 변경 입력에 잘못된 응답 재사용0건 |
| W10 | 계측·기계 조립/정비 추가 | W04,W06 | 같은 앱의3팩 | 각 팩 질문·미확인·보고서 완주 |
| W11 | 새 추론 선택 경로 | W07, 사용 가능한 서버 | 제한된 live 기능 | 큐·오류·시간·재개 추적 |
| W12 | 학생/강사 자료·배포 | W10 및 팩별 W08/W09 또는 명시적 제어 모드 | 웹·ZIP·활동지·진행안 | 팩별 응답 커버리지 확인, 새 환경에서 결과 저장 |
| W13 | 교실 장애 리허설 | W12 | 리허설 기록·수정 | 네트워크/모델/음성 실패 시 완주 |

먼저 W01→W03→W04→W05/W06의 **전자 조립 한 건**을 완성한다. 나머지 영상 정리와 문서 작업은 병렬로 진행할 수 있다. 실제 모델 응답 수집은 문서와 입력 계약이 정해진 후 한다. 응답을 먼저 수집한 다음 전혀 다른 규칙/프롬프트에 연결하는 순서는 피한다.

새 추론은 선택 기능이지만 **실제 응답 재현을 표방하는 배포에는 W08이 필수**다. 모델 실행을 못 했다면 제어 실습 버전으로 공개 범위를 명시하고 실제 응답이라고 부르지 않는다.

W08/W09는 전자 조립만 통과하면 끝나는 공통 체크가 아니다. 계측·기계/정비 각각의 제공 분기에 실제 응답이 있는지 확인한다. 팩별로 `실제 응답 있음 / 교육용 입력 / 작업자 입력 / 미지원` 표를 만들고, 미지원 분기를 실제 응답 버튼으로 실행하지 못하게 한다.

## 24. 강의까지의 제작 순서 제안

제공된 일정표의11월26일 특강을 기준으로11월21–25일을 다음처럼 사용한다. 이는 작업 순서 제안이며 실행 완료 예상 시간을 보증하는 일정은 아니다.

|---|---|---|---|

| 11/23 | 실제 응답팩 연결이 가능한 범위 확보 | 계측·정비 UI 재사용 | 모델 응답 재현과 fixture 구분 |

현재 GPU 중단 때문에 새 모델 응답 확보는 일정의 외부 의존성이다. CPU 설계·문서·앱 준비와 분리해 관리한다. 별도 촬영이11/23까지 준비되지 않으면 다지점 측정·키팅을 이번 기본팩에 넣지 않는다.11/25에는 새로운 모델이나 복잡한 프레임워크를 추가하지 않는다.

시간이 부족할 때 우선 줄일 것은 live 자유 입력, ASR, 키팅, 자동 도면 부위 추정이다. 줄이지 않을 것은 실제 문서 처리, 출처 구분, 질문 연결, 미확인 기록, 보고서 저장이다.

## 25. 검수와 공개 완료 조건

### 소프트웨어 동작

| 검수 사례 | 기대 동작 |
|---|---|
| 정상 예제 정보 구축 | 원문 필드와 DB 일치 |

| 미도래 조건 | 불일치 대신 미도래 |

| 다른 제품/질문에 답변 | 현재 항목에 자동 적용하지 않음 |
| 소수점 불명확 | 원문 보존, 허용 범위로 값을 추정하지 않음 |
| 단위 누락/잘못된 장비 | 수치 합격 계산 전 유효성 보류 |
| 영상 끝 | 필수 검토 전 전체 승인하지 않음 |

| 모델 실패/시간 초과 | 실패/미확인 보존, 몰래 성공 응답 대체 금지 |

| 보고서 출력 | DB/기록의 값·판정·사진·모드가 일치 |

### 실제 인식과 교육 적합성

모델의 JSON 형식 성공, 실제 작업 인식, 제어기의 올바른 판정, 학생의 완주는 각각 측정한다. 최소한 정상·명확한 불일치·가림·아직 검사할 때가 아닌 장면을 구분해 검수한다. 원본 주석, 강사 검수, 교육용 합성 기대값의 권위를 섞지 않는다.

새 자료에서 실제 응답을 수집하기 전 [실험 체크리스트](PROJECT_NOTES.ko.md)를 해당 실행 경로에 작성한다. 이 설계 문서의 요구사항만으로 ‘상속 검증됨’이라고 기록하지 않는다. 프레임/정답 누출, 문서/BOM 누락, 질문 연결 오류, 잘못된 계측 수용이 하나라도 있으면 해당 기능의 공개 완료를 보류한다.

### 배포 리허설

Chrome/Edge 등 수업 대상 환경에서 신규 세션 → 자료 구축 → 세 팩 실행 → 질문/답변 → 보고서/ZIP 저장을 실제 확인한다. 영상 재생·탐색, 한국어 글꼴, PDF 페이지 잘림, 키보드 조작도 확인한다. 인터넷을 끊거나 모델 서버를 연결하지 않은 조건에서 기본 경로를 끝내 본다.

배포 전 파일 허용 목록 검사로 HTech, 개인 경로·계정·키, 모델 가중치, 원본 라이선스 누락을 확인한다. 준비된 공개 후보를 검수한 다음 저장소와 웹 배포를 진행한다. 이 계획 단계에서는 외부로 게시하지 않는다.

## 27. 최종 납품물

1. 학생이 바로 열 수 있는 한국어 실습 웹앱과 시작 링크.
2. 공개 코드 저장소와 전체 실행·제작 설명.
3. 세 가지 시나리오의 교육용 PDF/CSV/참조 자료.
4. 출처·라이선스·해시·시간 대응이 있는 영상/프레임팩.
5. 실제 요청·응답과 실패를 포함한 모델 응답 재현팩.
6. 구분된 교육용 제어 실습팩과 학생 활동지.
7. 검수조서·보고서·단일 HTML·CSV/JSON·증거 ZIP 출력.
8. 강사용 진행안, 예상 질문, 정상/오류/보류 설명.
9. 오프라인 강사 실행팩과 장애 대응 안내.
10. 실제 브라우저 E2E·인식 검수·배포 검수 기록.

첫 제작 완료 단위는 **전자 조립 한 사례에서 학생이 자료를 넣고, 정보를 구축하고, 영상을 진행하고, 질문에 답한 뒤 자기 실행 기록이 담긴 보고서를 내려받는 것**으로 정한다. 이 경로가 성립한 다음 동일 엔진에 다른 팩을 추가한다.
